# M2 가격 수집과 표면갭

## 실행

명령은 저장소 루트에서 실행한다.

```sh
uv sync --locked
uv run dexdda
```

서버가 시작되면 기존 `data/registry.json`, `config/settings.toml`, `.env`를 읽고 수집을 시작한다.
초기에는 값이 없으므로 stale이 보이며, 전체 유동성 조사와 첫 가격 순회에 수십 초가 걸릴 수 있다.
API 키를 바꾸면 서버를 재시작한다. 실행 중 자동으로 .env를 다시 읽지는 않는다.
M2는 OKX 인증만 사용하고 거래소 시세는 공개 API를 사용한다. 개인키·RPC·입금 주소는 필요하지 않다.

- [가격·갭 JSON](http://127.0.0.1:8000/api/gaps)
- [프로세스 상태](http://127.0.0.1:8000/api/health)
- 제한된 실제 검증: `uv run scripts/check_prices.py --seconds 35` (5~120초 허용, 종료 시 수집기도 정리)
- 종료: Ctrl+C

서버 실행 중 주기적으로 API를 호출한다. 검증 스크립트도 별도의 수집기를 실행하므로 상시 서버와 중복 실행하지 않는다.
유료 API 선택·결제·업그레이드는 수행하지 않는다. 한도 오류는 진단에 표시하며 자동 결제로 해결하지 않는다.

## 계산과 분류

`gap = CEX 현재가(KRW) / (DEX 가격(USD) × 업비트 KRW-USDT 매도 1호가) - 1`

업비트·빗썸 모두 같은 업비트 USDT 매도 1호가를 쓴다. 1 USD ≈ 1 USDT를 가정한다.
거래소 매도 및 USDT 매수 수수료는 포함하지 않는다. 표면갭이므로 체결 수량·슬리피지·가스·브릿지 비용도 반영하지 않는다.
이는 M4 실효갭 견적과 별개다.

- `main`: 한 거래소 이상에서 tradable인 토큰. 해당 체인을 직접 지원하는 거래소의 갭만 계산·정렬한다.
- `bridge_candidates`: 어떤 거래소에서도 tradable이 아닌 후보 토큰 중 같은 coin_id의 최대 유동성 체인 하나. 같은 코인에 별도의 메인 토큰이 있어도 후보 그룹은 존재할 수 있다.
- `suspected`: 계산 가능한 거래소 갭 중 하나라도 절댓값이 설정 상한(기본 30%)을 넘으면 이동한다. 정확히 ±30%는 초과가 아니다. `origin_section`으로 원래 분류를 보존한다.
- 거래소별 갭 중 큰 값 순으로 정렬하고, 계산 불가 항목은 아래에 둔다.
- 유동성 하한 미달 또는 communityRecognized=false이면 경고한다. 유동성·인식 여부 미확정도 경고한다. `unrecognized_action="hide"`면 이 행들을 숨기고 `counts.hidden`에 집계한다. 의심 목록 분리가 먼저 적용된다.

브릿지 체인 선택에는 전체 후보의 유동성이 필요하다. 한 체인이라도 조회가 빠졌거나 만료되면 최대값을 확정하지 않고
`liquidity_selection_pending`으로 남긴다. 이 행은 체인·주소·갭이 비어 있고 숨김 설정과 무관하게 보류 사유를 표시한다.
동률이면 숫자 체인 ID, 주소 순으로 고른다. 선택한 한 체인만 빠른 가격 폴링에 넣고, 전체 유동성은 더 느린 주기로 다시 비교한다.
모든 행의 `execution_enabled`는 false이며 브릿지 실행 경로는 없다.

## 데이터 만료와 복구

가격마다 수신 시각(`received_at_ms`)과 제공자 시각(`source_at_ms`)을 보관한다.
수신 후 경과 시간은 단조 시계로 측정하며 `stale_seconds`를 넘으면 stale이다.
거래소 현재가는 최근 체결값이므로, 정상 REST 스냅샷 재조회로 수신 신선도를 갱신한다. 최근 체결이 오래됐다는 이유만으로 정상 스냅샷을 실패로 처리하지 않는다.
DEX 가격과 USDT 호가는 제공자 데이터 나이도 검사해 오래된 가격/호가를 반복 응답받는 경우를 차단한다.
제공자 시각이 역순인 스트림은 덮어쓰지 않고, 5초 넘는 미래 시각도 거부한다. REST 현재가의 시각은 최근 체결을 뜻할 수 있으므로 이전 WS 시각보다 과거여도 받아들인다.
단, REST 요청 중 새 WS 값이 도착했다면 그 값을 유지한다.

빗썸 REST에서 숫자 timestamp가 UTC보다 9시간 앞서는 응답을 실측했다. 응답의 trade_date·trade_time(UTC)과 trade_timestamp를 대조해
정확히 9시간 차이가 확인되는 경우만 UTC로 정규화한다. 이미 UTC인 응답은 그대로 받아들이고, 불일치는 추측하지 않는다.
`provider_timestamp_offset_ms`에 보정량(0 또는 32400000)을 남긴다. WS에는 이 보정을 적용하지 않는다.

마지막 값은 참고용으로 반환하지만 stale 입력이 하나라도 있으면 해당 거래소의 `gap`과 `gap_percent`는 null이다.
한 거래소만 실패하면 다른 거래소의 계산은 유지한다. 공통 USDT 호가가 만료되면 두 거래소 갭 모두 계산하지 않는다.

유동성은 price-info 조회 수신 나이로 별도 만료시킨다. 이 응답의 time은 가격 시각이므로 유동성의 체결 시각으로 간주하지 않는다.
유동성 만료는 메인 목록의 경고/숨김과 브릿지 선택에 반영한다.

WebSocket 스냅샷·실시간 시세를 먼저 사용하며, 누락·오래된 종목만 REST로 보완한다.
연결이 끊기면 1~30초 간격으로 재연결한다. 정상 REST 대체값은 WS 단절로 무효화하지 않는다.
OKX 배치 일부가 누락되면 누락된 토큰만 stale 처리한다. 오류 원문·인증 헤더는 응답이나 로그에 넣지 않는다.

## 설정과 호출량

`config/settings.toml`의 `[pricing]`:

| 설정 | 기본값 | 의미 |
|---|---:|---|
| poll_seconds | 5 | 가격 순회 및 REST 보완 목표 주기 |
| stale_seconds | 15 | 가격 신선도 |
| okx_batch_size | 100 | OKX 요청당 토큰 수 |
| okx_interval_seconds | 1.1 | 가격·유동성이 공유하는 요청 최소 간격 |
| liquidity_poll_seconds | 300 | 전체 대상의 유동성 조사 주기 |
| liquidity_stale_seconds | 900 | 유동성 수신 데이터 만료 |
| rest_batch_size | 20 | REST ticker 요청당 종목 수 |
| rest_interval_seconds | 0.21 | 거래소별 REST 최소 간격 |
| ws_batch_size | 100 | 연결별 ticker 종목 수 |

주기는 목표이며, 순회가 오래 걸리면 이전 순회가 끝난 다음 시작한다. 중첩 순회를 만들지 않는다.
`diagnostics.cycles`의 소요 시간과 `interval_exceeded`로 목표 주기를 지키는지 확인할 수 있다.
현재 레지스트리의 메인 토큰은 312개이고, 실제 검증 때 브릿지 선택 222개를 합쳐 가격 조회 대상은 534개였다.
100개 배치면 가격 한 순회에 6회이며, 1.1초 간격에서 최소 약 6.6초가 필요하다. 네트워크 지연과 유동성 조사도 추가된다.
5초 내 모든 토큰 갱신을 보장하지 않는다. 유동성 초기 조사 대상 912개에는 10회 요청이 필요하다.
숫자는 레지스트리와 데이터 누락 상태에 따라 달라진다.

호출 제한 응답에는 공통 게이트에서 2~60초까지 대기 시간을 늘린다. 인증·권한·결제 필요 오류에는 60초 간격을 둔다.
무제한 즉시 재시도는 없다. 한도·과금 판단에는 장시간 수집 결과와 계정의 실제 정책 확인이 추가로 필요하다.

## API 응답

외부 요청은 백그라운드에서만 실행하고 `GET /api/gaps`는 메모리의 최신 상태를 반환한다.
금액·가격·갭은 Decimal로 계산하고 JSON에서는 문자열로 반환한다. gap은 비율, gap_percent는 퍼센트다.
시각은 Unix 밀리초다. 캐시는 `no-store`로 지정한다.

최상위 필드: `main`, `bridge_candidates`, `suspected`, `usdt_krw_ask`, `basis`, `counts`, `diagnostics`.
일반 행은 `coin_id`, `chain_index`, `address`, `dex_usd`, `liquidity_usd`, `exchanges`, `warnings`를 포함한다.
각 거래소에는 `route_status`, `price_krw`, `gap`, `gap_percent`, `stale`, `unavailable_reasons`, 입금 네트워크가 있다.
입출금 상태는 M1 레지스트리의 스냅샷이며 M2에서 실시간 갱신하지 않는다.

프로세스 살아 있음은 `/api/health`, 데이터 건강 상태는 각 stale 및 diagnostics로 구분한다.
설정/레지스트리 로드 실패는 `/api/gaps`가 비밀값 없는 503을 반환한다.
M3 목록 화면을 구현했다. [사용 안내](m3-dashboard.md)를 참고한다.
